# Dismissal Patterns

When a transient surface is open — a popover, menu, inline editor, panel — something has to
decide *when it closes again*. "Dismissal" is that behavior. This page defines the **three
dismissal patterns** we use, when to reach for each, and how the shared components handle the one
case Radix cannot see on its own: **iframe (WebView) boundaries**.

This is a UX pattern, not a component. Most surfaces are built on shadcn/Radix primitives that
already implement dismissal; your job is to pick the right pattern and wire the Radix props
accordingly.

> **Scope.** This page is about *which interactions dismiss a surface*. It is **orthogonal to
> modality** — whether the rest of the UI is inert and focus is trapped. A `Dialog` can be modal
> *and* use Explicit dismissal. Modal vs non-modal, touch long-press, and right-click context menus
> are out of scope here.

---

## Pick a pattern by how transient the surface is

The three patterns differ only in **which interactions dismiss the surface**. Read the table
top-to-bottom as "least sticky" to "most sticky".

| Pattern                  | Outside press | Escape | Outside scroll | Window loses focus |
| ------------------------ | :-----------: | :----: | :------------: | :----------------: |
| **Light dismissal**      |       ✓       |    ✓   |        ✓       |          ✓         |
| **Click-away dismissal** |       ✓       |    ✓   |        ✗       |          ✓         |
| **Explicit dismissal**   |       ✗       |    ✓   |        ✗       |          ✗         |

The last column is the **window losing focus** — focus moving into another frame, another
application, or DevTools. It counts as an outside press; see
[the iframe section](#the-iframe-webview-gap).

### Light dismissal

The surface gets out of the way the moment attention moves anywhere else — including a scroll.

- **Use for:** transient popovers, hover cards, and non-critical menus you only *glance* at — they
  should vanish the moment you look or scroll away.
- **Don't use for:** anything holding text the user is typing. (And not tooltips/hints — see below.)

### Click-away dismissal

Closes on a deliberate click elsewhere or Escape, but **stays open while the user scrolls** the
content behind it. This is the right default for popovers and panels that act as a temporary
"layer" over scrollable content.

- **Use for:** filter panels, detail popovers, secondary controls you might consult *while*
  scrolling the page behind them.
- **The scroll column is the whole reason this pattern exists** — it's the difference from Light.

### Explicit dismissal

Only a deliberate action closes it: Escape, a close button, or completing the task (submit /
select). Outside clicks, scroll, and window blur are **ignored** so the user never loses in-progress
work by accident.

- **Use for:** inline editors, comment composers, multi-step forms in a popover — anywhere an
  accidental outside click would discard work.

### Not on this axis: tooltips & hints

Tooltips and hints aren't a fourth, "weakest" pattern. This axis is about which **outside
interactions** dismiss an **open, interactive** surface; a tooltip does the opposite — it closes on
the *withdrawal* of what opened it (hover/focus leaving its trigger), not on an outside interaction.
Reach for the
[`Tooltip`](https://paranext.github.io/paranext-core/platform-bible-react-storybook/?path=/docs/shadcn-tooltip--docs)
primitive, which handles this (and stays out of the WebView gap below); don't wire a pattern from
this page.

## How to wire each pattern

Radix (shadcn) primitives expose the triggers as props on the content element:

| Trigger            | How                                                                                                                                  |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| Outside press      | `onPointerDownOutside` / `onInteractOutside` (portal-aware — see the iframe section)                                                 |
| Escape             | `onEscapeKeyDown`                                                                                                                    |
| Outside scroll     | **No Radix prop.** Add a `scroll`/`wheel` listener on the scroll container and close. `onInteractOutside` does *not* fire on scroll. |
| Window loses focus | Nothing to wire — the shared wrappers turn it into an outside press (see the iframe section); controlled surfaces without `onOpenChange` need their own `window` blur listener |

- **Light:** accept Radix's defaults (outside press + Escape), and add a scroll listener to close on
  ancestor/page scroll.
- **Click-away:** keep outside-press + Escape, and **don't** add scroll dismissal. Where a Radix
  primitive dismisses on ancestor scroll by default, suppress it.
- **Explicit:** call `event.preventDefault()` in `onPointerDownOutside` / `onInteractOutside` so the
  surface stays open; leave `onEscapeKeyDown` alone (Escape should still work) and drive closing
  from your own close/submit controls.
- **Surviving window blur.** Window blur is an outside press, so a surface that must stay open when
  focus leaves (anything the user is typing text into) does what it does to survive a real outside
  click: call `event.preventDefault()` in `onPointerDownOutside` / `onInteractOutside`, or control
  `open` without an `onOpenChange` handler. There is no opt-out prop. A picker with a search box is
  not such a surface — losing a half-typed filter is not losing work.
- **An explicit-dismissal picker: the compact `BookChapterControl`.** After the user clicks one of
  its quick-nav arrows (previous or next chapter or verse) the book list is hidden and the popover
  becomes a small stepper. A non-modal picker in that state stays open through outside clicks,
  window blur and focus leaving, because the user steps through chapters while working elsewhere.
  Only a click on its trigger, or Escape while focus is in the popover or on the trigger, closes it.
  A modal picker makes everything outside inert, its trigger included, so it keeps the normal rules
  and closes on an outside press and on Escape. A compact picker whose tab becomes hidden stays open
  on purpose; it closes through its trigger once the tab is visible again, or on Escape with focus
  in it. Clicks elsewhere
  still act where the user clicked; only the dismissal is prevented. Once the book list returns
  (the search input takes focus, or the user types), the normal picker rules apply again.

## Accessibility

Dismissal is a keyboard and screen-reader concern, not just a pointer one:

- **Restore focus on close.** When a surface closes, return focus to the element that opened it
  (WCAG 2.4.3). Radix primitives do this, with one deliberate departure in the shared wrappers:
  focus is **not** returned when it is already in a web view (`activeElement` is an iframe) or,
  inside a web view, when the window is not focused. Returning focus across frames blurs the window
  the user just moved to and closes the menu they opened there. In the main document an unfocused
  window can only mean the OS window was deactivated, so the shared wrappers focus the trigger
  themselves for keyboard users coming back from another application. After an outside interaction
  a non-modal `Popover` and a `Menubar` would skip that restore, while a modal `DropdownMenu` would
  restore anyway; the wrappers make the outcome the same for all three. Inside a web view focus
  stays where the user put it. The renderer's overlay service also leaves focus where the user moved
  it, with a wider check than the shared wrappers' iframe test: focus on any pane frame, on a
  focusable shell control outside the overlay, or on a tab the window service already reports as
  focused. `Select` follows the same rule through `SelectContent`. A
  hand-rolled dismissal (a `window` listener that sets your own state) runs *outside* Radix's
  lifecycle: it must not focus the trigger on a blur dismissal in a web view, or when the active
  element is an iframe (`shouldSuppressFocusReturn`); in the main document after an OS-level
  deactivation it should return focus to the trigger, as the shared wrappers do. It must call
  `trigger.focus()` on other dismissals (Escape, a choice) — otherwise keyboard users are stranded
  on a closed surface's dead anchor. A consumer `onCloseAutoFocus` that calls `preventDefault()`
  and then focuses something explicitly bypasses the rule, so it must gate that focus call with
  `shouldSuppressFocusReturn` (exported by this library, together with `isRunningInWebView`).
  Restoring focus is not the same as showing a focus ring: after a close the user drove with the
  pointer, the ring would sit on a control the pointer has left. Suppress the ring for that case
  rather than withholding the focus — see `TabDropdownMenu`, which marks its trigger with
  `data-quiet-focus` and clears the mark on the next keydown. The ring stays under forced colors
  (Windows High Contrast), where it is the only focus indicator left. For why the browser's own
  "focus without the indicator" option is not usable here, see the
  `adr-menu-close-focus-restores-without-the-ring` entry in
  `.context/standards/Architecture-Decisions.md`. The helpers behind this (`QUIET_FOCUS_*`,
  `useInteractionModality`) are internal to this library for now and not exported, so an extension
  cannot reuse them yet.
- **Exception: the editor toolbar's marker menus.** A pick from the paragraph-style menu returns
  focus to the Scripture text rather than to the button, since the pick acted on the text. A
  dismissal still returns focus to the opener, and the editor can be the opener: Enter on a selected
  paragraph marker opens the menu from the text, so dismissing that menu returns focus to the text.
  The character-marker menu returns focus to the text on every close. See the
  `adr-marker-menu-close-focus-follows-the-opener` entry in
  `.context/standards/Architecture-Decisions.md`; the dismissal rule may still change.
- **Escape closes the topmost surface only.** When surfaces stack (e.g. a popover inside a dialog —
  supported here via `PopoverPortalContainerProvider`), Escape should dismiss the innermost first.
  Radix handles this per layer; preserve it rather than adding a global Escape handler.
- **Don't trap focus unless the surface is modal.** Modal surfaces (`Dialog`) trap focus by design;
  non-modal surfaces (popover, menu) must not (WCAG 2.1.2). Modality is orthogonal to this axis.
- **Tooltips/hints** must stay hoverable, be dismissible with Escape, and not disappear on their own
  while hovered (WCAG 1.4.13). The `Tooltip` primitive handles this.

## The iframe (WebView) gap

Platform.Bible renders most WebViews as **`iframe`s**, and many are **cross-origin and sandboxed**
(see `src/renderer/services/web-view.service-shard.ts`). Radix detects an outside press by listening
for `pointerdown` on the document that owns the surface, and **a click inside an iframe never
produces a `pointerdown` in any other document** — in either direction. Left alone, a menu in the
main toolbar would stay open when the user clicks into a WebView, and a menu inside a WebView would
stay open when the user clicks the toolbar or another pane.

**Window blur is an outside press.** When the user clicks into another frame, the surface's own
window fires `blur`. `PopoverContent`, `DropdownMenuContent`, `MenubarContent` and
`ContextMenuContent` listen for it through `useDismissOnWindowBlur` and dispatch a synthetic
`pointerdown` just outside the surface, so Radix runs its normal outside-press path. Every surface
built on those components gets the behavior with nothing to wire, in the main window and inside
every WebView alike. The exception is a controlled surface without an `onOpenChange` handler that
should still close on blur: it needs its own `window` blur listener (the inline markers menus are
the example). Because it is the ordinary outside-press path, the opt-outs in
[How to wire each pattern](#how-to-wire-each-pattern) keep working, and a popover portaled into a
dialog through `PopoverPortalContainerProvider` closes while the dialog stays open.

A plain window switch (alt-tab, DevTools) also dismisses a Light or Click-away surface, as native
menus do.

Consequences to know about:

- The click that dismisses the surface is not swallowed. The pane it lands on receives it first, so
  it acts there (places a caret, focuses the pane) and the surface closes.
- Not wired: `Select` (it closes on window blur by itself; `SelectContent` applies the same
  focus-return rule), `Tooltip` and `Dialog` (not on this axis), sub-menu contents (dismissing the
  root closes them), and the Scripture editor's right-click menu (not Radix; its window-blur close
  is fixed separately in the editor package).
- Escape is not forwarded across frames. After a click into another frame, Escape goes to that
  frame.
- A modal menu opened inside a picker closes alone on a window blur; the picker stays open until the
  next blur or outside press, as it would after a real click outside both.
- Inside a web view, a dialog does not pull focus back from another frame when a picker nested in it
  closes on blur. Platform.Bible patches Radix's focus trap for this; web views built in other
  repositories carry their own copy of Radix and need the same patch until Radix fixes it upstream.

**Don't hand-roll containment against the trigger.** Radix portals content to `document.body`
(`lib/platform-bible-react/src/components/shadcn-ui/popover.tsx`), so the floating content is
**not** a DOM descendant of its trigger. A naive `trigger.contains(activeElement)` check reads the
surface's own content as "outside" and **dismisses itself**. Radix's built-in
`onInteractOutside`/`onPointerDownOutside` are already portal-aware — use them.

### Scroll inside a WebView is unobservable

Light is supposed to dismiss on outside scroll, but the parent **cannot observe scroll that happens
inside a cross-origin WebView**. Until the platform forwards WebView scroll up to the host, **Light
surfaces do not dismiss on scroll that occurs inside a foreign WebView** — press and window blur
still dismiss them. We deliberately do **not** approximate this from pointer position — treating
"pointer entered the WebView" as a scroll signal would conflate hovering with scrolling and dismiss
Light surfaces on mere cursor movement. The real fix is the **WebView forwarding its scroll events
to the host** (feasible over the existing channels — `papi.webViewProviders.postMessageToWebView` /
the reverse path for sandboxed WebViews, `window.parent.papi` for same-origin WebViews), which is
not built yet.

### Status

The window-blur dismissal lives in `useDismissOnWindowBlur`
(`lib/platform-bible-react/src/hooks/use-dismiss-on-window-blur.hook.ts`) and is applied by the
shared wrappers. There is no WebView scroll-forwarding capability yet, so in-WebView scroll won't
dismiss a Light surface.

See also: [Interactions](./application-interactions.mdx) for the menus and surfaces these patterns
apply to, and [Component Choices](./component-choices.mdx) for picking the surface in the first
place.

## Glossary

- **Outside-interaction dismissal** — umbrella term for closing a surface in response to interaction
  elsewhere (pointer, Escape, scroll, or the window losing focus). Mirrors Radix's
  `onInteractOutside`.
- **Light dismissal** — closes on *any* outside interaction, including scroll. (In UX writing,
  "light dismissal" is sometimes used generically; here it names this specific pattern.)
- **Click-away dismissal** — closes on outside press + Escape + the window losing focus,
  but **not** on outside scroll.
- **Explicit dismissal** — closes only on a deliberate action (Escape, close, submit); ignores
  outside press, scroll, and window blur.
- **Window blur** — the surface's own window losing focus (a click into another frame, alt-tab,
  DevTools). Treated as an outside press by the shared wrappers.

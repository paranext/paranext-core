# Standard View: Paratext 9 vs Paratext 10 — user-facing differences

**Audience:** Product Owner. Plain language; no code internals.

**Status:** Revised 2026-08-27 against the `standard-view` branches (paranext-core
[#2565](https://github.com/paranext/paranext-core/pull/2565), scripture-editors
[#545](https://github.com/eten-tech-foundation/scripture-editors/pull/545)). Supersedes the
2026-07-07 list, which was written at the Phase 5 wrap-up; a lot has landed since.

**How to read the Cost column:** what it would take to make PT10 match PT9, if we chose to. "Small"
= days, "Medium" = a focused work item (1–2 weeks), "Large" = its own project phase. Rows marked
"n/a — deliberate" are places we chose a different behavior on purpose and believe it is equal or
better; they can still be revisited.

**How rows were checked.** Rows marked ✅ were re-verified against the current branch (by reading the
shipped code or running its tests). Rows marked ⏳ are carried forward from the July list and have
not been re-confirmed by hand since. Rows marked 🆕 are new since that list.

---

## What behaves the same (the short version)

Typing and editing markers inline exactly as text (Standard view's core promise); the `\` marker
popup with type-through — you can type `\q1 ` without ever looking at the popup, Space commits,
Escape leaves your text alone; marker lists filtered to what is valid at your position (same
stylesheet rules as PT9, including your project's custom.sty); close-tag suggestions for open
character styles; non-basic styles dimmed the way PT9 greys them; footnote/cross-reference markers
offered mid-text; invalid or unknown markers highlighted in red as you type; Ctrl+Space clears
character styling; copy/cut/paste of marker text including whole USFM fragments; footnote and
cross-reference insertion with PT9's snippet shape and caret placement; project fonts, colors, and
custom styles driving the display; and documents containing tables, figures, and sidebars loading,
saving, and round-tripping with zero data loss.

## Where PT10 is better than PT9 (for balance)

- Unknown and invalid markers are flagged in red live, while the document stays byte-faithful.
- Copied text is normalized so it never carries invisible non-breaking spaces into other apps.
- Note callers are project-data-driven, with separate footnote and cross-reference sequences.
- Formatted note preview on caller hover.
- Lossless round-trip of unsupported structures is verified by an automated corpus, not hope.
- The note editor's type and caller dropdowns replace two PT9 dialogs with in-place controls.

## Open questions for the PO

1. **`\cat` on footnotes is data loss.** Typing a category into a footnote in Standard view silently
   discards it. Everything else on this list is a difference; this one is a defect. Worth deciding
   whether it blocks release.
2. **Selection + `\` + Space now wraps.** In PT9 that gesture does nothing. We filled it because
   "accepts a keystroke and discards it" is the failure mode we're most trying to avoid — but it is
   a new behavior, not parity, and it deserves an explicit yes.
3. **Marker glyph contrast** — match PT9's greys, or keep the current look?
4. **Marker descriptions are raw English** in every UI language. Acceptable for now?
5. **Enter always shows the paragraph menu.** PT9's SmartEnter users get one extra keystroke on
   every paragraph break. A "direct insert, no menu" mode is small if it's wanted.
